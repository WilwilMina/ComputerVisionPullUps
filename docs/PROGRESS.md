## Done
- Workspace set up per `docs/reference/` guide: `CLAUDE.md`, 2 rules, `qa` and `researcher` agents, one test hook, `.gitignore`, `requirements.txt`.
- **Slice 1** `pullup_rom/pose.py`: `PoseResult` (pixel keypoints `[F,33,(x,y,conf)]` + MediaPipe `world` 3D landmarks + fps), `PoseBackend` Protocol, `MediaPipePoseBackend` (heavy model, VIDEO mode), `.npz` cache, CLI with `--preview`. Frames with no person are NaN/conf 0, never zeros.
- **Slice 2** `pullup_rom/metrics.py` -> `Signals` (see "Slice 2 validity change" below for the current rules):
  - Low-confidence joints become NaN; gaps up to `MAX_GAP_S` are interpolated for the head, shoulders, elbows and body scale (NOT for the wrists that build the bar). Savitzky-Golay smoothing per contiguous valid run.
  - The one y flip to height-up happens in `compute_signals` (`up()`); angles do not need it.
  - `head_minus_bar` is divided by a body scale (shoulder width or torso length, rolling median) so it is unitless.
  - Elbow angle from both 3D world landmarks and 2D pixels; `ELBOW_ANGLE_SOURCE` picks which one the rep logic sees. `Signals.elbow_arms_used` flags which arm(s) fed each frame.
  - `pullup_rom/debug_plot.py`: head/bar/elbow plot. Grey = not valid, orange = bar carried from neighbouring frames.
- **Slice 2 validity change (this session).** `head_minus_bar` no longer needs visible wrists in the same frame:
  - The bar line is a rolling median (`BAR_WINDOW_S`) of wrist height over frames where a wrist was CONFIDENT and above the shoulders. Wrist positions are never interpolated or guessed for the bar.
  - A bar value needs at least `BAR_MIN_CONFIDENT_SHARE` of its window to be confident gripping frames, otherwise there is no bar value.
  - `Signals.bar_carried` marks frames that have a bar value although their own wrists were not confident; `bar_support` is the share per frame. `reps.Rep.peak_bar_carried` passes this to slice 3.
  - Only frames between the first and last confident grip count (`in_hang_span`). `head_valid` and `elbow_valid` replace the old single `valid`; the elbow keeps its own validity.
  - With the defaults the longest wrist loss the bar can bridge is about 1.5 s (window 2 s, share 0.25).
- **Slice 3** `pullup_rom/reps.py` (pure: numpy and config only): `detect_reps(head_minus_bar, elbow_deg, fps, RepParams, bar_carried)` -> `RepAnalysis(reps, discarded)`.
  - Hysteresis state machine on head height with debounce; a rep runs from the head's lowest point before the pull, through the peak, to its lowest point after lowering. The valley between two reps ends one and starts the next.
  - The elbow angle is read ONLY at the bottom: the MEDIAN angle over the bottom region (contiguous frames within `REP_BOTTOM_BAND_BODY_SCALES` of the valley's lowest head height) before and after the rep; `bottom_elbow_deg` is the lower (less extended) of the two. A median, not a maximum, because QA showed a maximum lets angle noise lift a bent bottom over the threshold (190 of 200 noisy reps); tested with 40 noise seeds both ways. The elbow at the top is never used (tested by overwriting it).
  - A rep's `start_frame` is the last frame at the bottom before the pull; its `end_frame` is the FIRST frame the head is back within `REP_BOTTOM_BAND_BODY_SCALES` of the low level the rep started from (not the lowest point of a long hang, which drifted late on 14293451). If it never returns that far it falls back to the region around its lowest point. `Rep.pull_time_s` = start to end (bottom to top to bottom; None if the clip ended mid-rep), `Rep.ascent_s` = bottom to top. Ascents shorter than `REP_MIN_ASCENT_S` (start to peak) are discarded as glitches (QA showed a 0.1 s blip counted as a rep).
  - FULL needs head clear AND bottom elbow at or above the dead-hang threshold. The threshold is `config.DEAD_HANG_ELBOW_MIN_DEG`, a per-source dict that is UNSET (`None`). While unset, a rep that clears the bar has `full=None` (shown UNKNOWN); a rep whose head fails is `full=False`. No "near 180 deg" value exists anywhere.
  - A missing-data gap longer than `REP_MAX_GAP_S` during a rep is kept conservative (user decision, no threshold changed to rescue the stock clips; revisit on the user's own footage), but never dropped silently: it is returned in `RepAnalysis.discarded` and printed as `uncertain (tracking gap)` with its time range. Glitches are listed as `ignored (too short to be a rep)`. A clip that ends mid-rep is flagged.
  - `pullup_rom/rep_report.py` prints each rep with start/end/bottom elbow angles: `python -m pullup_rom.rep_report data/cache/<clip>.npz [--source world|image]`; `eval_clips --reps` prints it per clip.
- **Evaluation** `python -m pullup_rom.eval_clips data/external [--cached-only] [--reps] [--no-plots]` (not in pytest; needs the model and videos; caches keypoints in `data/cache/`, writes `data/plots/`). Per clip: person %, invalid head / elbow / either %, bar carried %, median confidence for head/shoulders/elbows/wrists, head-landmark spread (nose, eyes, ears: how much they disagree on height, in body scales; agreement is not correctness, since from behind the face points are guessed), bar drift (first `EVAL_DRIFT_SKIP_S` seconds excluded) and scatter, elbow angle ranges for both sources, one-arm share. The old `head@top` column was removed: nose confidence stays high even from behind.

## Calibration (2026-10-09), first and only one
- **What the user said:** every rep in `pexels_10336041` and `pexels_6389831` is a full-ROM rep (their label; the project has no other ground truth).
- **Elbow, 3D (`world`):** the angle is the pose model's ESTIMATE of the 3D elbow angle, not a true joint angle: it reads about 145-155 on arms that look nearly straight. The 13 complete reps in those clips have bottom elbow angles 144.86 to 154.60 deg. `DEAD_HANG_ELBOW_MIN_DEG["world"] = 144.0`, the lowest whole degree at or below all of them: the strictest value that keeps every labelled rep FULL. One-sided: no bent-elbow examples exist, so it cannot say where a bent elbow begins. Two clips, two people.
- **Elbow, 2D (`image`):** the same reps read 129.9 to 161.3 deg (the two clips differ by about 25 deg: the 2D angle depends on the camera view), so no 2D value can be set; it stays unset.
- **Head margin:** unchanged (0.0). Rep 1 of `pexels_10336041` peaks at -0.55 body scales (head below the bar; frames show his head below his hands), so it is NOT FULL on the head check despite the label. The user's "all full" and the measured head height disagree on that one rep; the rep was kept for the elbow range only. `pexels_6389831` rep 4 is cut off by the end of the clip and was left out of the range.
- **Effect on the labelled clips:** `10336041` gives 9 FULL and 1 NOT FULL (rep 1, head); `6389831` gives 3 FULL and 1 UNKNOWN (rep 4, clip ended mid-rep).
- **Effect on the other clips (not accuracy, no labels):** `4964660` 3 FULL, `14293451` 3 FULL, `26586395` 3 NOT FULL on arms (bottoms about 136-141), `wikimedia` 2 NOT FULL on arms, `7672115` 2 FULL and 3 NOT FULL on arms, `35585615` mixed, `38226256` and `8233829` no reps. Whether those arm failures are bent elbows or just a lower 3D reading for that person and view is unknown. That is the main risk of a threshold set on two clips.
- **Rule added:** a rep the clip cuts off mid-rep is UNKNOWN, never FULL, because the return to dead hang was never seen.
- **Needed next:** labelled bent-elbow and chin-short reps to bound the threshold from the other side, then a held-out clip.

## Wrist-to-bar offset: measured, then APPLIED as 0.23 (own commit, 2026-10-09)
The hands wrap over the bar, so the bar sits above the wrist landmark. `python -m pullup_rom.bar_offset crops ...` writes zoomed crops with a pixel ruler about the wrist line; an agent read the bar's top, bottom and centre against the ruler (reads good to about 5 px on `6389831`, 2-4 px on `10336041`; `data/labels/offset_crops/` and `offset_readings_*.json`). `summarize` converts to body-scale units (offset in px over the pipeline's body scale at that frame; positive = bar above the wrist line).
- `pexels_6389831`: 12 usable frames of 14 (2 unreadable: open hands mid-jump; a dark band over the bar). Bar centre 55-75 px above the wrist line = mean 0.237, std 0.021, range 0.193-0.266 body scales. Bar thickness about 0.11.
- `pexels_10336041`: 10 usable frames of 12. Bar centre 16-20 px = mean 0.218, std 0.019, range 0.191-0.242. Bar thickness about 0.13. Caveat: the hands grip sloped handles of a multi-grip bar, so the value depends on where along the handle it is read.
- Pooled 22 frames: mean 0.228, std 0.022, range 0.191-0.266 body scales (centre of the bar). The top edge is roughly half a thickness (about 0.06) higher. Two clips, two people, hand-read.
- APPLIED by the owner's decision as a geometry measurement, not tuned to labels: `BAR_OFFSET_BODY_SCALES = 0.23` (pooled mean 0.228, rounded; the bar CENTRE, not the top edge). Effect: every `head_minus_bar` drops by 0.23, so a nose that only reaches the wrist line is now below the bar. On the four stock clips the scored verdicts did not change (their head check passed by more than 0.23). Unscored rep changes: `7187450` rep 9 now fails the head check (-0.09; it had been FULL) and rep 8 passes by 0.04; `6389831` rep 4 (label UNKNOWN: clip ended mid-rep, chin at or just over the bar by the owner's eye) now reads NOT FULL on the head check (peak about -0.12 against the bar centre), a disagreement with the label that is reported, not tuned away. Asking the model for several people in the same pass is not an option: with `num_poses=3` the same single person on `15859716` read a bottom elbow of 122.5 deg instead of 132.6 (about 10 deg lower; re-runs at `num_poses=1` are bit-identical), which would shift every calibrated number. So `POSE_NUM_POSES` stays 1 (comment in `config.py`).
Built: a second, people-check pass (`POSE_COUNT_NUM_POSES = 3`, provisional) that never touches the keypoints. It stores `people_count` per frame and `follow_check` per frame (1 the tracked person is the one hanging on the bar, 0 not, -1 not judged: one person, nobody hanging, or nobody tracked). "Hanging" = both wrists above the shoulders by position (wrist confidence is often low on a lifter). The CLI warns when 20% or more of frames show several people (`WARN_MULTI_PERSON_SHARE`) and when 20% or more of the judged frames follow someone not on the bar (`WARN_WRONG_PERSON_SHARE`); both cutoffs are provisional with no data behind them. `--no-people-check` skips the pass. Old caches without the arrays are never warned about.
Result on `10039581`: people histogram 0/1/2/3 people = 2/52/181/7 frames (78% of frames with several); of 143 judged frames, 79 followed the wrong person (55%). Single-person clips `15859716` and `7187450`: one person every frame, nothing to judge, measurements bit-identical to the old caches.
Limits: it WARNS, it does not switch to the right person; verdicts on such a clip are for the wrong person part of the time. A person with arms merely raised counts as hanging. Tested on synthetic skeletons and the one real clip.

## Unsupported-style flag (kipping), 2026-10-09
`pullup_rom/style.py`: median over reps of the torso tilt from vertical (3D world landmarks) at the rep bottoms; at or above `UNSUPPORTED_SWING_BOTTOM_TILT_DEG` (15, provisional) with at least 2 measurable reps the CLI adds an UNSUPPORTED STYLE warning (banner, console, JSON `warnings` and `style_checks`). It never changes a verdict or a measurement; the reps and verdicts are still printed. Tested on synthetic poses and, when the caches exist locally, on the real clips.
- Real clips: kipping `14284164` reads 23.1 and is flagged. Labelled non-kipping clips read 3.7-10.7 and are not flagged (`10336041` 6.3, `6389831` 7.5, `15859716` 3.7, `7187450` 10.7). One positive clip only, so the cutoff is a provisional midpoint, not a validated value.
- Two unlabelled clips are also flagged. By an agent's look at the frames (not the owner's): `14293451` (16.3) is kipping with clear leg swing, high confidence, plus a late stretch of knee raises that is not pull-ups; `35585615` (24.7) is a handheld close-up from behind with the hips and legs mostly out of frame, upper body looks strict, unsure and low confidence, so probably a false flag where the hip landmarks are guessed. So at least one likely false positive and one likely true positive beyond the labelled clip.
- Limits: from a front or back camera the fore-aft swing, the main part of a kip, is the least observable; a close-up that cuts off the hips makes the measure unreliable. Advisory only.

## Nose versus mouth, tracking confidence only (2026-10-09; NOT changed, proposal only)
Calibration clips with labelled reps: `10336041`, `6389831`, `15859716` (`10039581` is excluded). Over the hang span, nose and mouth (weaker of the two corners) both have median confidence 0.99-1.00 and 100% of frames at or above 0.5 on all three clips, including `15859716`, which is a BACK view where the face is not visible: BlazePose reports near-1.0 confidence for landmarks it is only inferring. So confidence cannot separate them. Geometry does: the mouth reads a steady 0.06-0.11 body scales (typically 0.07-0.08) below the nose at the top of every rep on all three clips. By the chin-over-the-bar definition the mouth is the nearer proxy to the chin (the chin is below the mouth, the nose is further above it), so it is the stricter and more faithful choice, but the gap between mouth and chin is unmeasured here. PROPOSAL (waiting for the owner): switch `HEAD_LANDMARKS` to the two mouth corners, with the offset and margin revisited together. The change moves every `head_minus_bar` down by about 0.07-0.08. Not applied.

## Idea, not built: per-person calibration from a reference clip
The 3D elbow angle is a model estimate that differs by person and camera view (the two labelled clips read about 145-155; others about 136-141 on arms that may be equally straight). Instead of one global threshold, a person could film a short reference clip of known-good reps (a few full pull-ups with a real dead hang), and the tool would derive that person's own bottom-angle level from it (for example the lowest bottom angle across the reference reps) and set the threshold relative to it, same camera setup. It needs the person's labels, a rule for how far below the reference counts as bent (which needs bent examples), and a guard against a reference clip that is itself not full. Nothing of this is built; the global 144 stays.

## Known limitations
- The dashed bar line on frames marked `bar (carried)` can sit visibly off the real bar (QA saw about 20 px on street_bar), because it is a median of other frames' wrists; the banner wording says 'lack a usable head or elbow signal', and a skeleton is still drawn on those frames.
- Rolling-median edges: the first/last half window of a clip is biased toward the interior under camera drift (at most slope x window / 4).
- The wrist joint is not the top of the bar. `BAR_OFFSET_BODY_SCALES` (0.23, measured on two clips) corrects for this. A mean of two wrists is also wrong for a tilted bar or a side view (8233829).
- Head landmark: BlazePose has no chin; the nose is a placeholder, and from behind the face points are guessed. Head-spread agreement does not prove they are right.
- If one forearm is missing the elbow angle uses the other arm (flagged in `elbow_arms_used`, nothing yet acts on it). If a whole body side is missing, body scale is NaN. If any `HEAD_LANDMARKS` entry is missing the head signal is NaN.
- Rep detection is untested on real footage beyond the printed tables; the start-rise, end-drop and bottom-band values are placeholders and were not chosen from measured hang jitter.
- Rep end time is now the first return to the starting low level. If the head never returns within `REP_BOTTOM_BAND_BODY_SCALES` of it (a rep that finishes high), the end falls back to the region around its lowest point.
- A head-signal gap longer than `REP_MAX_GAP_S` mid-rep still makes that attempt uncertain: the bar is NaN because too few wrists were confident. This costs a real rep on 26586395 and 7672115 (now listed as `uncertain (tracking gap)` with a time range, not hidden). Revisit on the user's own footage.
- A rep's bottom is the less extended of the valleys before and after it, so one bent valley fails both neighbouring reps (by design, as a rep must start from and return to dead hang).

## Constraints and decisions
- Sandbox proxy blocks model downloads (`storage.googleapis.com` returns 403). Pose extraction must run on the user's machine.
- MediaPipe 1.1.0 is installed here; the Tasks API (`PoseLandmarker`) is unchanged. Model file: `models/pose_landmarker_heavy.task` (gitignored).
- Python: `.venv` built with 3.13. The test hook prefers `.venv`.
- Downloads: nothing is fetched onto the user's PC without their say-so for that specific file. The dev-clip rules (sources, HEAD-check, 100 MB cap, own directory, verify before use, never delete) are recorded in `data/external/SOURCES.md` and apply to any new clip.
- BrowserOS neo: the researcher agent can now see it (verified with a diagnostic run), after the tools entry was corrected.
- Line endings: the repo is LF (`.gitattributes`: `* text=auto eol=lf`); a clean commit re-stored 14 files that had been committed as CRLF. If a tool writes CRLF, git normalizes it on add.
- Git: local repo on `main`, remote `origin` = https://github.com/WilwilMina/ComputerVisionPullUps.git (set, never pushed by Claude). Commit identity is repo-local: the user's name and their GitHub no-reply address. Rule (user, in CLAUDE.md): after each slice passes tests and `qa`, commit locally; run `git status` first and confirm nothing from `data/`, no videos, model files or `.env` is staged and the layout matches `.claude/rules/architecture.md`. Never push; the user pushes. History so far: scaffold commit, then one commit for slices 1-3, then one per slice. `docs/reference/*.pdf` is gitignored. Security scan: `tools/scan_sensitive.py` runs from `.githooks/pre-commit` (staged changes) and `.githooks/pre-push` (every commit being pushed). It blocks videos, model files, `.npz` caches, PDFs, archives, keys and `.env`; anything under `data/`, `samples/`, `out/`, `models/`; files over 1 MB; private keys and common API-token shapes; secret-looking assignments; personal absolute paths and email addresses; and commits whose author or committer email is not a GitHub no-reply address. Findings are redacted (emails show only the domain). QA review fixed: a quadratic regex on long lines (now linear; a 5 MB line scans in under a second), `sk-proj-` keys, JSON/dotenv-style secrets, case-variant file names, merge-commit content. Known limits: encoded or split secrets, secrets in commit messages, unquoted letters-only values; a few false positives (e.g. numpy `A@B.shape` reads as an email; use `scan:allow`). Its 3 throwaway-repo tests are marked `slow` (`pytest -m slow`) to keep the default suite near 2 s. Enable it after cloning with `git config core.hooksPath .githooks`; never bypass with `--no-verify`. Also worth switching on in the GitHub repo settings: secret scanning and push protection.
